## Что нужно, кроме Python

| Навык | Метка | Зачем в этом модуле |
|---|---|---|
| `collections`, `ast`, `math`, регулярное чтение чужого кода | 🛠 Hard | инструменты, чтобы превратить рассуждение в проверяемый код |
| Аналитический склад ума: гипотеза → проверка → вывод | 🧠 Мышление | искать причины, а не угадывать |
| Стратегическое мышление: выбирать с учётом роста | 🧠 Мышление | решение, которое работает на 100 данных, может не пережить 100 000 |
| Системное мышление: видеть связи между частями | 🧠 Мышление | любое изменение задевает не только то место, где вы его сделали |
| Инженерный подход: разбить на части и проверять после каждого шага | 🧠 Мышление / 🛠 Hard | большое делают маленькими безопасными шагами |
| Оценка сроков и уточняющие вопросы | 🤝 С людьми | большинство проблем начинается с непонятной постановки |

Метки в заданиях: 🛠 — код с автопроверкой · 🧠 — рассуждение с автопроверкой · 🤝 — практика без автопроверки: образец ответа и критерии.

## Что это и зачем

Хороший инженер отличается не тем, что знает больше функций, а тем, как действует, когда задача непонятна или код ломается.
Здесь каждое задание — это небольшая «рабочая ситуация»: выбрать, измерить, найти причину, разобрать на части, оценить влияние.

## 📖 Теория карточками

### 🃏 Сначала измерь, потом решай
Про скорость нельзя гадать: нужно мерить. Но одного замера мало. Смотрите, **как растёт время, когда данные вырастают вдвое**. Вдвое — значит O(n). Вчетверо — O(n²). Почти не изменилось — O(1) или O(log n).

### 🃏 Выбор с оглядкой на рост
Для 100 записей подойдёт любое решение. Для 100 000 разница между «пройти весь список для каждого элемента» и «посмотреть в словарь» — это секунды против часов. Стратегия: подумайте, **какая операция будет частой** и что случится, если данных станет в 100 раз больше.

### 🃏 Найти причину
Когда программа падает, не меняйте код наугад. Выпишите допущения, на которые функция опирается (формат, не ноль, не пусто). Затем **нарушьте каждое допущение** и посмотрите, что произойдёт. Это и есть гипотеза → проверка → вывод.

### 🃏 Большое — маленькими шагами
Огромную функцию трудно понять и невозможно проверить целиком. Разбейте её на части с понятными именами, проверяйте каждую часть и только потом соберите заново. Если после сборки результат такой же, вы ничего не сломали.

### 🃏 Всё связано
Функции вызывают друг друга. Изменили одну — задели те, кто её вызывает, а затем тех, кто вызывает их. Прежде чем менять, спросите: **кого это заденет?**

<details><summary>Образец ответа</summary>

1. «Кто пользуется отчётом и что ему сейчас мешает?» (цель и пользователь)
2. «Что значит "удобнее": быстрее открывается, читается проще или выгружается в другой формат?» (смысл слова)

**Задание 9. Предскажи вывод (без запуска).** Сколько раз выполнится сравнение `items[i] == items[j]`?

```python
def has_duplicates(items):
    for i in range(len(items)):
        for j in range(i + 1, len(items)):
            if items[i] == items[j]:
                return True
    return False


has_duplicates([1, 2, 3, 4])
```

<details><summary>Ответ</summary>

6 раз: 3 сравнения для `i = 0`, 2 для `i = 1` и 1 для `i = 2`. Формула `n(n − 1) / 2`: для 4 элементов 6, для 1 000 уже 499 500. Это **O(n²)**.

</details>

## 💡 А знаете?

Фраза «преждевременная оптимизация — корень многих проблем» взята из статьи Дональда Кнута 1974 года. Но он тут же добавил: в действительно важных примерно 3 % кода оптимизировать нужно. Поэтому инженеры сначала **измеряют**, где именно медленно.
Подробнее: [Knuth on go to, 1974 (разбор статьи)](https://blogs.mathworks.com/steve/2009/08/27/knuth-on-go-to-1974/), [Is premature optimization the root of all evil?](https://blog.startifact.com/posts/is-premature-optimization-the-root-of-all-evil/).
